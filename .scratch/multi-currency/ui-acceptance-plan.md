# 多币种页面职责重构验收执行计划

> 状态：冻结，等待实现后执行。
>
> 用例来源：[多币种 UI 对抗式验收脑暴](./ui-acceptance-brainstorm.md)。实施开始后，用例的判断标准不随实现调整；若产品边界确实变化，必须先由主 agent记录原因并更新产品意图。

## 执行角色

实施者不能担任最终验收者。最终验收 subagent 使用全新上下文，只读取产品意图、实施方案、55 条验收用例、Git diff 和运行中的应用。它可以创建验收报告与临时日志，不能修改产品代码或测试来让结果变绿。

## 固定数据与运行环境

- API 和组件测试使用隔离的临时 SQLite 数据库，不接触正式 `data/budget.db`。
- 浏览器验收使用脑暴文件中的“基准家庭”。优先通过用户主动点击“载入示例数据体验”得到基础数据，再补充专门夹具；不能把测试专用账户写进正式数据库。
- 本地浏览器验收使用生产构建启动方式，并记录实际 URL、日期、视口和语言。
- 正式服务验收只做可恢复的读取和低风险交互；需要写入的场景先在本地隔离库完成。ser8 上重点核对页面职责、现有样例数据、服务状态和控制台错误。

## 自动化门禁

按顺序执行，任一步失败就记录实际输出并停止发布：

```bash
npm run typecheck
npm test
npm run build
git diff --check
rg -n '\.(only|skip)\(' src server
```

最后一条搜索应无输出。Vitest 必须报告零失败；Vite 体积提示可以作为非阻塞警告记录，但不能掩盖构建退出码。

## 用例分组与通过条件

| 验收轮次 | 用例 | 通过条件 |
| --- | --- | --- |
| 页面职责与导航 | MCUI-001—005、055、057 | 全局活动币种消失；三个页面各自持有 URL 状态；无效参数有提示、有回退、无串页和迟到覆盖 |
| 预算与家庭协作 | MCUI-007、009—012、048—054、063 | 预算按币种隔离；空状态能解释；共享结构有确认；revision 覆盖全部写入口；409 不丢输入 |
| 币种启停与账户 | MCUI-013—017、019—023 | 支持目录与家庭启用范围严格分开；停用保护完整；账户默认值和锁定状态与服务端一致 |
| 交易表达 | MCUI-025—030、064 | 银行入账和商户计价、转出和入账都有标签；筛选可组合；跨币种不出现错误总计 |
| 收支与投资 | MCUI-031、032、034—038 | 收支默认展示全部活动币种且分别统计；投资独立；内部调拨和估值不污染收入支出 |
| 家庭净资产与 FX | MCUI-039—047 | 默认币种和临时折算分开；总数可复算；缺率不补零；来源、方向和用途说明可理解 |
| 多语言与可访问性 | MCUI-058—061 | 中英文角色完整；键盘可操作；390px 与 320px 不丢关键动作；动态提示与图表有文本语义 |
| 系统回归与离线 | MCUI-065—066 | 认证和迁移锁优先；示例数据仍需主动加载；原币工作流不依赖 FX 网络 |

所有 P0 必须通过。P1 若受限于 VoiceOver 等人工环境，可以标为“需要人工复核”，但必须同时给出已经完成的自动化证据、未验证部分和明确操作步骤；不能标成通过。

## 对抗式抽查

最终验收者必须额外做四类交叉检查：

1. 在代码中搜索 `activeCurrency`、`setActiveCurrency` 和旧的 `sidebar_budgetCurrency`，确认没有第二套活动币种继续控制页面。
2. 枚举所有会影响预算读模型的服务端写路由，对照 revision 测试表，确认没有只改主要分配接口而漏掉交易、对账、账户关闭、目标或跨币种转账。
3. 分别追踪 `supportedCurrencies` 和 `enabledCurrencies` 的 UI 与 API 调用点，确认只有消费原始币种能使用“支持但未启用”的代码。
4. 在报表响应和 React 图表中搜索 `null`、`|| 0`、`?? 0` 等缺率处理，确认不完整净资产不会在图表、tooltip 或导出路径被补成零。

## 验收报告格式

最终结果写入 `.scratch/multi-currency/ui-acceptance-result.md`，至少包含：

- 被验收的 commit SHA、分支和工作区状态。
- 每条门禁命令、退出码、测试文件数与测试数。
- 每个 MCUI 用例的 `通过／失败／需要人工复核`、证据位置和备注。
- 浏览器使用的 URL、语言、视口、截图或可观察文本，以及控制台错误。
- 所有失败的最小复现步骤；验收者不得顺手修复。
- 正式部署后的服务 SHA、服务状态和最小 smoke 结果。
- 最终结论只能是“通过”“有条件通过”或“不通过”。任何 P0 失败时只能判定“不通过”。
