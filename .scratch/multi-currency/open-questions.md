# 多币种方案决策记录

> 状态：未决事项为零。用户已于 2026-08-30 确认首版币种目录、可启用范围和默认启用项。
>
> 使用方式：本文件保留已经确认的选择、理由和改变成本。后续需要改变时，先修改对应条目，再同步更新 `plan.md` 的明确结论。

## 投资管理做到余额还是持仓

已确认方案：沿用 YNAB 的跟踪账户，只记录投资账户总余额、净投入、净取回和估值日期。通过对账更新券商账户的市场价值，不管理证券标的、数量、成本基础、行情和收益率。

选择理由：用户当前需要按币种查看投资并纳入总资产。余额跟踪足以满足这个目标，也与现有 `investment` 预算外账户模型一致。没有持仓和现金流时点，账户余额变化不能可靠称为投资收益。

如果改变：需要单独设计证券、持仓批次、交易、行情、公司行动、费用和收益计算，数据模型及报表都会明显扩大。

## 分类结构在币种之间共享还是各自维护

已确认方案：分类组、分类名称和备注共享；分配额、目标、活动和可用金额按币种分开。用户只维护一套“餐饮”“房租”等分类结构，同时可以给 USD 和 CNY 设置不同预算。

选择理由：YNAB 的资金隔离来自每个 plan 只有一种货币，不要求分类名字必须不同。共享分类减少重复维护，也符合个人财务跨币种比较的使用习惯。

如果改变：完全独立的分类树需要给分类增加账本归属，并设计复制、同步和跨币种报表映射。

- [x] 已确认

## 同一币种是否允许多个预算账本

已确认方案：一份数据库代表一个家庭共享预算空间，首版每种币种只有一个预算账本。两位家庭成员可以各自拥有多个账户；双方的同币种预算账户共同参加该币种预算，并共同使用一份 `Ready to Assign`。账户和流水仍分别保存，不会互相覆盖。

选择理由：家庭共同管理一份预算时，共享可分配资金正是预期行为。只有双方希望各自维护互不可见的同币种预算时才会发生模型冲突；这需要成员身份、账户所有权、隐私和权限，已经超出本轮家庭共享模型。

如果改变：`currency_code` 不能再作为账本标识，需要引入独立 `ledger_id`、成员与权限模型，汇总时还要增加账本和成员筛选。

- [x] 已确认

## 支持哪些货币和资产单位

用户已确认：首版内置支持目录包含 CNY、USD、SGD、CAD、EUR、GBP、JPY。G7 国家对应 USD、CAD、EUR、GBP、JPY 五种货币，再加 CNY 和 SGD，共七种。JPY 使用零位小数，其他六种使用两位小数。

概念区分：内置支持目录是产品能够正确处理的币种集合；`currency_ledgers` 是当前家庭实际启用的子集。用户可以随时从内置目录添加币种账本。

已确认方案：新家庭默认启用 CNY、USD、SGD、JPY、EUR。CAD 和 GBP 在内置目录中保持可选，用户可以通过 Settings 或新建账户流程启用。首版不允许用户输入任意三位代码或自行设置小数位。

扩展约束：目录外法定货币由后续产品版本扩充内置目录；数据库只约束三位大写代码，因此扩充目录不需要迁移既有财务表。新增目录项仍需补齐最小单位元数据、Provider 覆盖、契约测试和界面验证。

- [x] 已确认：首版内置目录加入 SGD
- [x] 已确认：用户从内置目录启用币种，默认启用 CNY、USD、SGD、JPY、EUR

## 自动汇率使用哪个来源

已确认方案：Frankfurter v2 作为首版默认 HTTP Adapter，并固定 `providers=ECB`。参考汇率只用于资产负债估值。实际换汇以银行真实转出额和到账额为准。用户可以输入人工汇率，人工值优先。

选择理由：该接口无需密钥，支持历史日期和来源筛选，首版七种货币在目标来源覆盖内，也可以自托管。ECB 参考汇率适合信息展示，不适合作为成交保证，方案按这个限制使用。

扩展约束：FX Module 依赖厂商无关的 Provider Interface。`FrankfurterEcbAdapter` 和测试用的 `InMemoryFxAdapter` 实现同一接口，并通过同一套契约测试。以后接入 MAS、银行或付费数据源时新增 Adapter 和 Provider 注册项；报表接口、人工覆盖规则和财务数据 Schema 不变。新来源的数据许可、币种覆盖和历史深度仍需单独核对。

- [x] 已确认

## 缺少汇率时是否显示部分总数

已确认方案：任何有非零余额的币种缺少汇率时，统一净资产标记为不完整，不显示总资产、总负债和净资产数字。页面仍展示原币余额、已换算明细与缺失列表。

选择理由：把缺失账户当零或悄悄排除会生成一个可读但错误的总数。财务总览应优先保证口径完整。

如果改变：可以显示“已覆盖账户小计”，但必须使用不同名称，并明确覆盖比例，不能仍叫总资产或净资产。

- [x] 已确认

## 历史净资产采用当时汇率还是今天汇率

已确认方案：每个月使用月末当日或之前最近工作日的汇率。今天的汇率只用于今天的净资产。

选择理由：历史曲线应回答“当时按统一币种价值多少”。用今天的汇率重算全部历史会让过去曲线随着当天汇率漂移，也会掩盖真实汇率影响。

如果改变：可以另加“按当前汇率重估历史”的分析视图，但不能替换标准历史净资产。

- [x] 已确认

## 是否需要汇总币种下的收入支出报表

已确认方案：首版收入、支出、预算和投资都按原币分别查看；只有资产、负债和净资产换算到汇总币种。净资产变化中的汇率影响不归入收入或支出。

选择理由：用户明确希望收入、支出和投资分别统计，最终统一查看资产负债。现金流折算还要决定交易日汇率、月均汇率和汇兑差额，属于另一套报表口径。

如果改变：需要新增交易日汇率快照和汇兑影响分解，不能直接拿月末汇率换算整月收支。

- [x] 已确认

## 换汇和投资调拨是否进入普通收支

已确认方案：币种账本之间的换汇按 YNAB 规则影响源分类和目标 `Ready to Assign`，但两条腿从普通 Income v Expense 中排除，并单列为“币种调拨”。预算账户与投资跟踪账户之间的转账也从普通收支排除，改由投资视图统计净投入和净取回。

选择理由：应用能够通过 `pair_id` 识别资产内部调拨。把 `100 USD` 换成 `700 CNY` 同时记成支出和收入，会夸大两个币种的日常现金流；投资本金从银行移到券商也没有减少净资产。

如果改变：可以完全模仿 YNAB 独立 plan 的报表表现，让转出分类进入支出、目标币种流入进入收入。预算计算不用改变，只需调整报表筛选口径。

- [x] 已确认

## 外币刷卡是否保留商户原始金额

已确认方案：保留可选的原始币种和原始金额。预算、账户余额和收支报表只使用银行最终按账户币种入账的金额。

选择理由：原始金额有助于核对小票和银行换算，但信用卡对账必须以账单入账币种为准。两个金额承担的用途不同。

如果改变：可以删除辅助字段以缩小范围，代价是外币小票和账单之间只能靠备注核对。

- [x] 已确认

## 账户币种创建后能否修改

已确认方案：空账户可以修改；存在非期初流水的账户禁止修改。币种填错后新建正确账户，并通过转账迁移余额。

选择理由：直接修改会重新解释全部历史整数，尤其在 JPY 与两位小数币种之间会永久改变金额含义。

如果改变：需要一套显式的全历史重算迁移，包含精度变化、流水、预算、目标、对账和审计记录，不能做成普通编辑字段。

- [x] 已确认

## 旧账本币种如何确定

已确认方案：升级后由用户在一次性迁移页确认。系统可以根据旧符号提出建议，但不静默映射。迁移前自动备份，金额按旧两位小数和目标币种精度换算。

选择理由：符号不能唯一确定币种。一次错误的自动映射会让全部历史余额和预算失去原有单位。

如果改变：可以为全新、无数据的数据库直接使用系统地区建议；有存量金额的数据库仍应保留确认步骤。

- [x] 已确认
