## 测试要证明什么

多币种功能完成后，系统需要同时守住四件事：原币金额没有被错误解释，预算不会跨币种串账，跨币种转账的两端金额能够对账，统一净资产可以按指定日期和列报货币复算。

测试以 Module 的公开 Interface 为主要入口。Money、Currency Ledger、FX、Budget 和 Reports 的行为尽量通过各自 Interface 验证。HTTP Route 只补鉴权、参数校验和响应形状，页面测试只验证用户能看到和完成的操作。这样内部重构不会迫使大量行为测试跟着改。

发布门槛包含自动化测试、旧数据库副本迁移演练和浏览器手工验收。Frankfurter 属于外部服务，标准测试套件不访问公网；生产 Adapter 使用受控的 `fetch` 响应测试，FX Module 使用 `InMemoryFxAdapter` 测试。

## 当前测试基础与实施前基线

仓库已经具备下面的测试能力：

- Vitest 2.1.9 统一运行 `server/**/*.test.mjs` 和 `src/**/*.test.{ts,tsx}`。
- 后端测试可以在临时目录中创建真实 SQLite 数据库。
- Route 测试通过随机本机端口启动 Express，再使用原生 `fetch` 调用 HTTP Interface。
- React 页面使用 jsdom、Testing Library 和 `fireEvent` 验证界面行为。
- CI 使用 Node 20，依次运行 `npm ci`、`npm run typecheck`、`npm test` 和 `npm run build`。

2026-08-30 在本机 Node 25.8.1 下执行了现有 `npm test`。解除沙箱的本机端口限制后，结果为 35 个测试文件通过、2 个失败，242 个测试通过、6 个失败。六个失败都来自现有 `BudgetPage` 测试，错误为 `localStorage.clear is not a function`。这些失败尚未证明与业务代码有关，也不属于多币种改动。

2026-08-31 由 Grok 4.6 xhigh 在 Node 20.20.2 下建立功能分支基线。typecheck 通过，37 个测试文件和 248 个测试通过，production build 通过。Node 25 下出现过的六个 Storage 失败没有在 Node 20 复现，因此没有修改测试代码。首次测试启动失败来自本地 `better-sqlite3` 的 Node 25 ABI；使用 Node 20 重建本地依赖后恢复，CI 的 `npm ci` 不受影响。

## 测试遵循的规则

- 每项行为先写失败测试，确认失败原因正好对应缺少的能力，再写实现。
- 金额、预算、汇率和报表测试断言精确整数或十进制字符串，不使用模糊容差。
- SQLite 属于本地可替代依赖。迁移、账本写入和报表测试使用真实临时数据库，不用对象 Mock 代替数据库约束和事务。
- Frankfurter 属于外部依赖。测试注入受控 `fetch`，不在 CI 访问真实服务。
- 时间相关测试固定时钟、配置时区和估值日。测试结果不能取决于执行当天、机器地区或周末状态。
- 每个测试自行创建数据，禁止读取或修改 `data/budget.db`。
- 测试只断言 Interface 可观察结果，包括返回值、数据库最终状态、HTTP 响应和页面内容。私有函数、SQL 执行顺序和中间对象不作为稳定契约。
- 新 Interface 测试覆盖旧浅层测试的全部行为后，删除重复测试，保留能够发现独立故障的回归用例。
- 不提交 `.only`、无理由的 `.skip` 或只断言“没有抛错”的测试。

## 测试夹具保持固定

复杂财务结果统一使用一组可手算的家庭夹具。金额先按界面显示值描述，写库时转换为相应币种的最小货币单位。

| 账户 | 币种 | 余额 | 预算属性 |
| --- | --- | ---: | --- |
| 家庭 CNY 日常账户 | CNY | 100,000.00 | 预算内 |
| CNY 信用卡 | CNY | -5,000.00 | 预算内 |
| USD 投资账户 | USD | 10,000.00 | 跟踪账户 |
| SGD 日常账户 | SGD | 5,000.00 | 预算内 |
| JPY 现金 | JPY | 100,000 | 预算内 |
| EUR 备用账户 | EUR | 0.00 | 预算内 |

估值日固定为 2026-08-30。该日期没有新的 ECB 工作日汇率，测试缓存提供 2026-08-28 的汇率：

| 货币对 | 汇率定义 | 汇率 |
| --- | --- | ---: |
| USD/CNY | 1 USD 等于多少 CNY | 7.20 |
| SGD/CNY | 1 SGD 等于多少 CNY | 5.40 |
| JPY/CNY | 1 JPY 等于多少 CNY | 0.050 |

按账户分别换算后，预期总资产为 CNY 204,000.00，总负债为 CNY 5,000.00，净资产为 CNY 199,000.00。EUR 账户余额为零，即使没有 EUR/CNY 汇率也不影响完整性。

家庭共享预算另建两个名称不同的 CNY 账户，分别代表两位家庭成员。首版没有成员字段，账户名称只用于让测试结果容易辨认。两个账户的收入都应进入同一份 CNY `Ready to Assign`，账户和流水仍各自保存。

换汇固定场景为 `100.00 SGD` 转出并实际到账 `550.00 CNY`，隐含汇率为 `5.5 CNY/SGD`。外币刷卡固定场景为商户原始金额 `20.00 EUR`，USD 信用卡最终入账 `-22.00 USD`。

## 测试辅助代码先收口

多币种测试会频繁创建数据库、启动 API 和准备汇率。实现首个检查点时增加少量测试辅助代码，避免每个文件各写一份容易漂移的初始化逻辑。

| 辅助能力 | 建议位置 | 约束 |
| --- | --- | --- |
| 创建临时数据库并在结束后关闭 | `server/test-support/database.mjs` | 每个用例或测试组独立目录，不接触生产数据库 |
| 启动测试 API | `server/test-support/http.mjs` | 显式绑定 `127.0.0.1`，等待 `listening` 后再读取端口 |

| 固定汇率 Provider | `server/test-support/fx.mjs` | 记录调用参数，可配置成功、缺失、超时和错误 |
| 前端 Bootstrap 夹具 | `src/test-support/fixtures.ts` | 同时包含支持币种、已启用币种和汇总币种 |

测试辅助代码只负责安排数据，不复制业务计算。预期净资产、预算和隐含汇率继续在测试中明确写出，避免夹具自己调用生产逻辑后得到一个无法独立核对的“预期值”。

## Money Module 用边界值锁定金额含义

Money Module 同时承担输入解析、最小单位、格式化和汇率换算。后端与前端应复用同一份币种目录，并运行同一组数据驱动用例。

币种目录需要验证：

- 内置目录恰好包含 CNY、USD、SGD、CAD、EUR、GBP、JPY。
- 新家庭默认启用 CNY、USD、SGD、JPY、EUR，CAD 和 GBP 仅在用户选择后启用。
- JPY 的最小单位位数为零，其余六种货币为两位。
- 公共写入 Interface 拒绝小写代码、长度错误和目录外代码。
- 测试目录临时加入 AUD 后，可以创建 AUD 币种账本，数据库 Schema 不需要改变。
- 重复启用同一币种得到幂等结果，不生成第二个账本。

金额解析与格式化至少覆盖：

| 输入或操作 | 预期结果 |
| --- | --- |
| `CNY 12.34` | 保存为 `1234` |
| `USD -0.01` | 保存为 `-1` |
| `SGD 1,234.50` | 保存为 `123450` |
| `JPY 123` | 保存为 `123` |
| `JPY 123.4` | 拒绝输入，不能静默四舍五入 |
| `USD 1.234` | 拒绝输入，不能丢弃第三位小数 |
| 超过 `Number.MAX_SAFE_INTEGER` 的结果 | 拒绝并返回明确错误 |
| `JPY 123` 的中文与英文格式化 | 都不显示小数位，并显示 JPY 或日元符号 |
| `SGD 1234` 的明确地区格式化 | 保持两位小数，结果不依赖测试机器地区 |

用户输入超出币种精度时直接拒绝。汇率换算产生的多余小数在最后一步按目标币种精度四舍五入。测试固定使用十进制定点输入，覆盖正数、负数、零和恰好位于半单位边界的值，确认正负数采用一致的四舍五入规则。

格式化测试显式传入 locale，避免不同 Node 或操作系统使用不同空格和符号形式。业务测试优先断言整数金额和币种代码，只有 Money 与页面展示测试断言格式化字符串。

## 旧数据库迁移先证明可恢复

迁移测试使用当前最后一个旧 Schema 版本创建真实 SQLite 文件，填入账户、交易、分配、目标、分类和历史月份，再调用正式迁移 Interface。测试不能手工模拟迁移后的最终表。

Schema 升级和用户确认的数据变换分开测试：

- 启动升级只增加兼容字段和迁移状态，不猜测旧币种，不重写金额。
- 有存量数据时，Bootstrap 返回 `currencyMigrationRequired`，财务写操作保持锁定。
- 用户确认后，数据变换前先生成可打开的备份。备份内仍是变换前的金额与 Schema 状态。
- 整个数据变换位于一个事务中。任一表转换失败时，原数据库保持未完成状态，不留下部分新金额。

迁移矩阵至少包含：

| 旧库情况 | 用户选择 | 预期结果 |
| --- | --- | --- |
| 两位小数旧库 | CNY | 所有金额整数保持不变，默认五个账本创建完成 |
| 两位小数旧库 | SGD | 所有金额整数保持不变，SGD 只创建一次 |
| 两位小数旧库 | CAD | 默认五个账本加 CAD，共六个账本 |
| 所有金额都能整除 `100` | JPY | 账户、交易、分配和目标金额统一除以 `100` |
| 任一待迁移金额不能整除 `100` | JPY | 阻止提交，返回表名、记录 ID、字段和原值 |
| 空数据库 | 无需确认 | 直接初始化默认五个账本并进入首次设置 |
| 目录外代码 | 任意旧库 | 服务端拒绝，不创建账本也不写完成标记 |

每次成功迁移都核对：

- 所有业务表的记录数量与主键集合不变。
- 每个账户的期初余额与交易合计能够复算出迁移后的账户余额。
- CNY、USD、SGD、CAD、EUR 和 GBP 的预算结果与升级前显示值一致。
- JPY 的账户余额、每月 `Ready to Assign`、分类可用金额和目标全部按一百比一缩放。
- 默认启用项与用户确认币种取并集，没有重复行。
- 第二次调用完成 Interface 返回“已完成”，不会再次缩放金额或再建备份。
- 迁移中断后重新启动仍停在确认页，已有数据没有被后台改写。

迁移失败的原子性测试可以在临时数据库里加一个只用于测试的 SQLite 触发器，让中途写入明确失败。断言所有待变换表都保持原值，比 Mock 某条 SQL 更接近真实故障。

## 预算测试按币种读取同一套 YNAB 规则

`computeBudget` 的测试入口必须显式传入 `currencyCode`。每条现有预算规则都需要在带币种的 Interface 下继续成立，包括收入、期初余额、分类活动、未分类支出、超支、目标、对账差额和资金账龄。

核心隔离场景如下：

| 场景 | 预期结果 |
| --- | --- |
| CNY 收入后读取 CNY 预算 | CNY `Ready to Assign` 增加 |
| 同一数据下读取 SGD 预算 | 数值不受 CNY 收入影响 |
| SGD 工资入账 | 只增加 SGD `Ready to Assign` |
| 两个家庭 CNY 账户各有收入 | 两笔收入相加进入同一份 CNY `Ready to Assign` |
| 两个账户名称相同 | 账户与流水仍按 ID 分开，不发生覆盖 |
| CNY 和 SGD 都给“餐饮”分配金额 | 分类元数据共享，分配、目标、活动和可用金额各自独立 |
| 同币种预算内转账 | 两个账户余额改变，预算整体保持中性 |
| 跨币种预算内换汇 | 源币种减少“换汇转出”，目标币种增加 `Ready to Assign` |
| CNY 流入参与资金账龄 | SGD 支出不能消费这笔 CNY 流入 |

查询测试还要故意放入其他币种的相同月份、相同分类和相近金额，防止遗漏 `currency_code` 条件时测试仍然碰巧通过。

## Currency Ledger Module 负责所有财务写入

`postTransaction`、`postTransfer` 和 `reconcileAccount` 是主要测试面。Route 与 AI 的测试确认它们调用这些 Interface，金额守恒和事务细节只在 Module 测试中完整覆盖。

普通交易测试包括：

- 记账金额始终按账户币种解释，调用者不能另传一个冲突的记账币种。
- `originalCurrencyCode` 与 `originalAmountMinor` 同时为空或同时存在，只有一个字段时拒绝。
- EUR 原始消费与 USD 入账金额同时保存，预算和账户余额只使用 USD 金额。
- 收入、支出、期初余额和对账调整继续保持原有正负号语义。
- 有非期初流水的账户拒绝修改币种。只有零余额且没有业务流水的空账户允许修改。

转账测试覆盖全部预算属性组合：

| 场景 | 重点断言 |
| --- | --- |
| 同币种预算内到预算内 | 两腿绝对值相同、共用 `pair_id`、预算中性 |
| 同币种却提交不同两端金额 | 服务端拒绝，两边都不写入 |
| 异币种预算内到预算内 | 两腿使用实际金额，源分类和目标 `Ready to Assign` 正确 |
| 异币种只提交一端金额 | 服务端拒绝，不能套参考汇率补值 |
| 预算内到跟踪账户 | 源分类减少，普通收支报表排除内部调拨 |
| 跟踪账户到预算内 | 目标币种增加 `Ready to Assign` |
| 跟踪账户到跟踪账户 | 只改变账户余额，不改变预算 |
| `100 SGD` 到 `550 CNY` | 两边余额分别变化，隐含汇率显示为 `5.5 CNY/SGD` |

事务原子性使用真实 SQLite 验证。在第二条转账腿写入时人为触发数据库错误，随后确认第一条腿、`pair_id` 和预算副作用都没有残留。编辑或删除任一转账腿时，继续运行现有成对更新与成对删除回归，禁止产生孤腿。

对账测试分别覆盖 CNY、JPY 和投资跟踪账户。调整金额必须使用账户币种；投资估值调整改变账户余额并进入净资产，同时从普通 Income v Expense 排除。

## FX Module 只相信规范化记录

Provider 契约测试以同一个用例集合运行 `InMemoryFxAdapter` 和 `FrankfurterEcbAdapter`。Frankfurter Adapter 注入假 `fetch`，测试可以核对请求和返回值，又不会受真实服务可用性影响。

每个 Adapter 都需要证明：

- 接收 `base`、`quotes`、`fromDate` 和 `toDate`，返回规范化记录。
- 每条记录含实际 `rateDate`、`baseCurrency`、`quoteCurrency`、正十进制 `rate` 和稳定 `source`。
- Frankfurter 请求固定包含 `providers=ECB`，请求体或 URL 不包含账户名、余额和流水。
- 厂商返回空结果、非法数字、未来日期、非成功 HTTP 状态和超时时，错误被归一化为 FX Module 能处理的类型。
- Adapter 不把厂商响应对象透传给调用者。

FX Module 的汇率选择需要覆盖：

| 缓存与请求情况 | 预期选择 |
| --- | --- |
| 同币种换算 | 直接返回 `1`，不调用 Provider |
| 估值日有直接汇率 | 使用直接汇率 |
| 只有反向汇率 | 精确取倒数并保留来源日期 |
| 只能经 EUR 连接 | 使用同一有效日期的交叉汇率 |
| 同日有人工值和自动值 | 使用人工值 |
| 较早人工值与较新自动值并存 | 先选不晚于估值日的最近日期，再在同日按来源优先级选择 |
| 估值日为 2026-08-30，最后数据为 2026-08-28 | 回退到 2026-08-28，并返回实际来源日期 |
| 缓存已有合适记录 | 不调用 Provider |
| 首次请求补齐缓存 | 第二次同参数调用不再访问 Provider |
| Provider 失败但缓存可用 | 返回缓存并保留其日期和来源 |
| Provider 失败且缓存缺失 | 返回明确缺失币种对，不编造汇率 |
| 只有估值日之后的记录 | 视为缺失，禁止向未来取值 |

可扩展性通过一个最小替代 Adapter 验证。测试把 Provider 注册项从 `frankfurter_ecb` 切到假来源，Reports Module 的调用和返回结构保持不变，人工覆盖优先级也保持不变。

真实 Frankfurter 连通性只做发布前可选 Smoke Test。该检查使用专门脚本、明确的环境开关和固定小额币种请求，不进入 `npm test`，也不以当天市场数值作为断言。它只确认请求协议仍可用、返回来源为 ECB，并打印实际汇率日期。

## 报表测试必须能够手算复核

原币报表通过 `buildNativeReport` 测试。每次只返回一个币种的收入、支出、分类构成、投资余额和币种调拨。测试中同时放入其他币种数据，确认结果没有串入。

统一净资产通过 `buildNetWorthReport` 和 `InMemoryFxAdapter` 测试。固定家庭夹具应得到 CNY 204,000.00 总资产、CNY 5,000.00 总负债和 CNY 199,000.00 净资产，并同时满足：

- 账户明细换算金额之和等于报表总额。
- 正余额进入资产，负余额绝对值进入负债。信用卡正余额按资产处理。
- 每个账户先换算并四舍五入，再汇总。
- CNY 账户使用汇率 `1`，不产生外部调用。
- 汇率元数据带回请求估值日、实际采用日期和来源。
- 零余额 EUR 账户缺汇率时不影响完整性。

账户级四舍五入使用一个专门反例锁定。两个 USD 账户各有 `0.01 USD`，汇率为 `7.5 CNY/USD`。每个账户分别得到 `0.08 CNY`，汇总结果必须是 `0.16 CNY`；先汇总再换算会得到 `0.15 CNY`，测试应能抓住这种实现偏差。

历史净资产至少准备三个月数据，验证：

- 每个月先计算月末原币余额，再取月末当日或之前最近的汇率。
- 修改 2026-08-30 的人工汇率不会改变 2026-07 月末净资产。
- 修改 2026-07-31 的人工汇率会重算对应历史月份，并显示人工来源。
- 账户在 `starting_balance_date` 之前不出现在余额或总额中。
- 当前净资产和历史最后一个点在相同估值日使用同一口径。
- 汇率变化和投资估值调整改变净资产，但不会进入原币收入或支出。

缺失汇率测试给 SGD 保留非零余额并移除 SGD/CNY 汇率。响应必须标记为不完整，停止输出总资产、总负债和净资产，同时继续返回原币余额、已换算账户和缺失列表。测试不得接受把 SGD 账户按零计入的结果。

换汇与投资调拨测试通过 `pair_id` 准备交易，确认它们出现在专门的币种调拨或投资净投入明细中，并从普通 Income v Expense 排除。

## HTTP Interface 只补边界和响应契约

Route 测试继续启动真实 Express，但共享的测试 Server 必须等待 `listening` 事件，并显式绑定 `127.0.0.1`。这样可以消除当前直接读取 `server.address()` 的时序假设。

重点验证：

- Bootstrap 返回支持币种、已启用币种、汇总币种和迁移状态。
- 预算、原币报表和净资产请求缺少必填币种时返回 `400`。
- 新建账户使用目录外币种、异币转账缺少到账金额、原始币种与金额只传一个字段时返回 `400`。
- 服务端按账户实际币种判断转账类型，不相信前端声明。
- HTTP 金额字段统一使用 `amountMinor` 等明确命名，响应顶层带币种。
- 迁移未完成期间，读取迁移状态可用，财务写入被拒绝。
- FX 同步和人工汇率接口不允许未来日期、非正汇率和目录外代码。
- 现有鉴权、错误 JSON 形状和备份 Route 回归继续通过。

预算计算、金额换算和转账矩阵不在 Route 层重复穷举。Route 测试选一个成功场景和每类校验失败，Module 测试负责完整行为。

## React 页面验证用户能完成完整操作

前端测试沿用 Testing Library，断言可见文字、表单状态和 API 调用参数。避免断言 Tailwind class、DOM 层级和整页 Snapshot。

| 页面 | 自动化行为 |
| --- | --- |
| Settings | 显示默认五种已启用币种，可启用 CAD 或 GBP，可切换汇总币种，可查看汇率日期和来源 |
| Accounts | 新建账户必须选择内置币种，默认值来自当前账本，列表按币种显示原币小计 |
| Budget | 切换 CNY 与 SGD 时请求相应 `currencyCode`，旧币种数据不会短暂当成新币种显示 |
| Transactions | 每行按所属账户币种格式化，JPY 不显示小数，外币消费展示原始金额 |
| Transfer 表单 | 同币种只需一个金额，异币种必须填写两端金额，并显示可复算的隐含汇率 |

现有 BudgetPage 测试的 Storage 问题只在 Node 25.8.1 下出现过，Node 20.20.2 的绿色基线没有复现。当前不修改测试 Setup；如果后续支持 Node 25，再用独立故障复现和修复处理，避免混入多币种行为测试。

首版不以引入 Playwright 作为自动化门槛。当前逻辑可以由 Module、真实 SQLite、HTTP 和组件测试覆盖，完整浏览器流程进入发布前手工验收。后续若多次出现组件测试抓不到的路由或状态同步回归，再单独引入浏览器 E2E。

## AI 与 IM 必须和网页共用写入规则

AI 测试不调用真实模型。假 LLM 返回明确工具调用，测试确认工具参数、待确认记录和最终数据库状态。

需要覆盖：

- `run_sql` 可以读取允许的财务视图，所有财务表写入都被拒绝。
- `fx_rates`、迁移状态和内部设置禁止 AI 写入，现有设置与聊天表继续保持不可读写。
- 普通交易使用 `post_transaction`，跨币种转账使用 `post_transfer`，对账使用类型化工具。
- 网页与 AI 用相同输入调用 Currency Ledger Module，得到相同校验错误和最终流水。
- AI 为 USD 账户记账时使用 USD 最小单位，不再统一宣称金额为“分”。
- 小票只有 EUR 原始金额、缺少 USD 最终入账金额时，AI 进入待确认或追问状态，不调用参考汇率自动补账。
- 批准写入后 `changed=true`，拒绝或校验失败后 `changed=false`，现有确认行为保持不变。
- IM 账户快照和确认文案按账户币种格式化，JPY 金额没有两位虚假小数。

收紧 SQL 权限前，先为现有 AI 写入能力建立功能对等测试，包括创建账户、分配预算、设置目标、对账和修改分类备注。类型化工具全部通过后再删除任意 SQL 写入路径。

## 故障与性能检查关注可观察退化

性能检查先记录基线，不在没有测量数据时写一个武断的毫秒阈值。测试数据至少包含七种币种、五年月份、多个预算内和跟踪账户，以及足以覆盖月末历史的交易。

需要留下这些结果：

- 同一净资产请求第一次只批量拉取缺少的日期和币种，第二次不发外部请求。
- Provider 调用次数按缺失日期和币种批次增长，不能按账户逐个请求。
- 历史报表不会为每个账户逐月重复查询同一汇率。
- 五年历史报表在开发机和 CI 上记录耗时与峰值内存，和改动前的单币种报表基线并列保存。
- Provider 超时、数据库约束失败和迁移中断后，原币记账或原始数据库仍保持可用状态。

如果实测出现明显退化，再根据真实基线设定 CI 阈值。查询计划可用 `EXPLAIN QUERY PLAN` 人工核对索引命中，但测试不绑定 SQLite 输出文本。

## 手工验收按家庭真实使用顺序执行

自动化测试全绿后，用全新临时数据库完成一次浏览器验收：

- 首次进入时确认默认启用 CNY、USD、SGD、JPY、EUR，CAD 和 GBP 仍可添加。
- 把 CNY 设为汇总币种，创建家庭 CNY 日常账户、CNY 信用卡、USD 投资账户、SGD 日常账户和 JPY 现金。
- 用两个不同名称的 CNY 账户模拟家庭两个人，各录一笔收入，确认共同增加 CNY `Ready to Assign`，流水没有互相覆盖。
- 分别给 CNY 和 SGD 的“餐饮”设置预算，切换账本后核对分配和余额互不影响。
- 记录 `100 SGD` 换成 `550 CNY`，核对两端账户、换汇分类、目标币种待分配资金和隐含汇率。
- 在 USD 信用卡记一笔 `20 EUR` 原始金额、`-22 USD` 最终入账的消费，核对预算只扣 USD。
- 把 USD 投资账户对账到新的总价值，确认投资视图和净资产更新，普通收入支出不增加。
- 导入固定汇率后，核对 CNY 204,000.00 总资产、CNY 5,000.00 总负债和 CNY 199,000.00 净资产。
- 删除 SGD/CNY 汇率，确认统一总数隐藏、SGD 缺失项可见；补录人工汇率后总数恢复。
- 断开网络，继续录入原币交易和预算，再打开已有缓存的净资产并核对汇率日期。
- 切换界面语言，检查新增中英文文案、币种代码和金额格式。

再用一份生产数据库副本完成迁移验收。整个过程都在副本上进行：

- 迁移前记录文件校验值、Schema 版本、各表行数、账户余额、每月 `Ready to Assign`、分类可用金额和净资产。
- 启动新版后确认系统要求用户选择旧账本币种，原数据库文件旁生成升级前备份。
- 选择实际旧币种并完成迁移，逐项对照迁移前记录。
- 关闭并重新启动应用，确认不会重复迁移或重复缩放。
- 从升级前备份恢复到另一个临时路径，确认旧版本能够打开并得到迁移前结果。

生产数据库副本、备份和验收截图都不得提交进仓库。记录中只保留脱敏统计和结果。

## 测试计划完成的定义

本测试计划落实完毕时，可以从每条产品结论追到一个自动化测试或明确的手工验收项；每个测试又能指出它验证的公开 Interface 和可观察结果。任何财务数字失败都能定位到原币金额、预算隔离、账本写入、汇率选择或报表汇总中的一个责任面，不需要靠浏览整个应用猜测原因。
