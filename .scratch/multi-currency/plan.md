## 采用的产品口径

一份本地数据库代表一个家庭共享预算空间，里面维护多个相互隔离的币种账本。家庭成员可以各自拥有多个账户；同一币种的所有预算内账户共同参加该币种的预算计算，也共同使用一份 `Ready to Assign`。成员在不同设备选择预算账本时不会互相切换页面；同一币种账本的并发写入通过 revision 检查，避免后一笔修改静默覆盖前一笔。

首版不引入成员身份、账户所有权、私密分类、按成员拆分的 `Ready to Assign` 或成员权限。两个人若希望在同一个应用实例中各自维护互不可见的 CNY 预算，就需要同币种多账本与权限模型，留给后续独立设计。

每个账户只有一个账户币种，每个预算内账户只参加同币种的预算计算。分类名称和备注可以共享，分配额、目标、分类余额、收入、支出和 `Ready to Assign` 都带币种，任何预算计算都不会直接相加两种货币。

用户另选一个全局的列报货币。文档和数据模型使用会计术语“列报货币”，设置页显示“净资产默认币种”，家庭净资产页的临时控件显示“折算为”。系统在净资产报表里按指定估值日换算各币种余额，得到统一口径的资产、负债和净资产。换算结果只是一层报表视图，不会回写账户余额，也不会修改历史流水。

这套设计沿用 YNAB 的两项核心做法：

- 每个 spending plan 只使用一种币种。多币种场景为每种币种建立独立 plan，换汇在转出 plan 记流出，在转入 plan 记流入。小文把这些 plan 收进同一个应用，并称为币种账本。
- 投资账户作为预算外的跟踪账户维护余额。投资余额进入净资产，不进入日常支出或 Income v Expense。

依据见 YNAB 的 [多币种指南](https://support.ynab.com/en_us/using-multiple-currencies-in-ynab-a-guide-SyBF6PHno?mobile-help=true)、[投资跟踪账户指南](https://support.ynab.com/tracking-investment-accounts-a-guide-r1Bzjxd05?mobile-help=true) 和 [Net Worth 说明](https://www.ynab.com/blog/ynab-reports-and-data)。“列报货币”采用 [IAS 21](https://www.ifrs.org/issued-standards/list-of-standards/ias-21-the-effects-of-changes-in-foreign-exchange-rates/) 的定义，即财务报表呈现所使用的货币。

## 目标范围

方案交付后，用户可以完成这些工作：

- 为现金、银行、信用卡、贷款、投资、房产等账户选择首版内置支持币种：CNY、USD、SGD、CAD、EUR、GBP、JPY。
- 在每个币种账本中独立分配资金、设置目标、查看收入、支出和分类结余。
- 在账户币种中录入和对账，同时保留外币消费的原始金额作为辅助信息。
- 在两个币种之间记录实际转出金额和实际到账金额，系统显示由两端金额推导出的实际汇率。
- 按币种查看投资账户余额和变化，定期通过对账更新市场价值。
- 选择一个汇总币种，查看当前和历史的总资产、总负债与净资产。
- 在汇总结果旁核对估值日期、实际采用的汇率日期、汇率来源和缺失项。
- 断网时继续完成原币记账和预算，并使用已经缓存的汇率查看可计算的历史报表。

G7 国家使用五种货币：美国使用 USD，加拿大使用 CAD，法国、德国和意大利使用 EUR，英国使用 GBP，日本使用 JPY。首版再加入 CNY 和 SGD，共内置七种货币。用户可以从这七种货币中按需启用币种账本。新家庭默认启用 CNY、USD、SGD、JPY、EUR，CAD 和 GBP 保持可选。

“内置支持币种”表示首版对金额精度、格式化、迁移和自动汇率做完整保证。首版界面不允许用户输入任意三位代码创建目录外币种。以后增加其他法定货币时，只扩充受版本控制的币种目录并补齐测试，不迁移既有财务表。让用户自行定义币种及最小单位属于后续独立功能。

本轮不做证券持仓、标的数量、成本基础、行情接入、已实现收益、未实现收益或税务损益。投资账户按 YNAB 的余额跟踪模型交付。目录外法定货币、贵金属、积分和加密资产留给后续独立设计。

## 当前代码需要改变的原因

当前模型把所有金额当作同一种货币：

- `server/migrations.mjs:19-68` 的账户和交易没有币种字段，交易只有整数 `amount`。
- `server/db.mjs:68-70` 只保存一个全局 `currency_symbol`。
- `src/format.ts:3-21` 用同一个符号格式化所有金额，并固定按两位小数解释整数。
- `server/engine.mjs:47-169` 把所有预算内账户放进同一个 `Ready to Assign`。
- `server/routes.mjs:828-840` 为转账写入绝对值相同的两条腿，无法表达 `100 SGD` 换成 `550 CNY`。
- `server/engine.mjs:233-335` 直接累加全部账户余额，未经过汇率换算。
- `server/ai.mjs:135-197` 把所有金额告诉模型为“分”，并允许 AI 绕过业务逻辑直接写财务表。

现有报表还有一处必须随本功能统一的口径：当前资产负债总额按账户类型分类，历史曲线按余额正负分类。新实现统一采用余额符号计算，正余额计入资产，负余额的绝对值计入负债，净资产等于资产减负债。信用卡出现正余额时会作为资产参与净资产计算，符合账户实际可支配价值。

## 金额和币种的领域规则

### 内置支持币种和家庭已启用币种

Money Module 内部维护一份受版本控制的币种目录。首版目录包含 CNY、USD、SGD、CAD、EUR、GBP、JPY，并保存每种货币的最小单位位数。`currency_ledgers` 只保存当前家庭已经启用的币种，是内置目录的一个子集。新家庭初始化时创建 CNY、USD、SGD、JPY、EUR 五个币种账本。

Settings 页的“添加币种”列出尚未启用的内置币种。新建账户只允许选择已经启用的币种，并提供“管理币种”入口；创建账户不能隐式启用账本。存在账户、交易、预算分配或目标的币种，以及当前净资产默认币种，都标记为“使用中”，不能直接停用；用户必须先更换净资产默认币种。消费原始币种不受启用范围限制，因为它只记录商户计价信息，不创建账本、不参与余额或收支计算。首版不接收用户手写的目录外代码，也不允许用户自行指定最小单位位数。

数据库只约束币种代码为三个大写字母，不把七种代码写死在表结构里。产品以后扩充内置目录时，只需增加目录记录、Provider 覆盖和契约测试；既有数据库不需要为新增币种迁移 Schema。

### 账户币种决定入账单位

每个账户有不可为空的 `currency_code`。交易的记账金额始终使用账户币种，交易行不重复保存记账币种。这样可以避免账户币种与交易币种发生冲突，也能让账户余额继续通过期初余额加流水求和得到。

账户一旦存在非期初流水，币种不可修改。错误币种通过新建正确账户并转移余额解决。空账户允许修改币种。

### 金额使用最小货币单位

数据库继续保存整数，但含义从“分”改成“最小货币单位”。`CNY 12.34`、`USD 12.34` 和 `SGD 12.34` 都保存为 `1234`，`JPY 123` 保存为 `123`。首版内置目录中，JPY 使用零位小数，其余六种货币使用两位小数。所有输入、格式化、四舍五入和安全整数校验集中在 Money Module 中，业务代码不再出现固定的乘除 `100`。仓库新增一份前后端共用的币种元数据，最小单位位数以这份受版本控制的数据为准；`Intl.NumberFormat` 只负责本地化展示，不决定数据库精度。

接口和 TypeScript 变量统一使用 `amountMinor`、`startingBalanceMinor` 等名称。数据库旧列名暂时保留，避免为了命名重建所有大表；迁移注释和 Schema 文档明确这些列保存最小货币单位。

### 外币消费保留原始金额

银行卡最终以账户币种入账，该金额决定预算和余额。交易可以额外保存 `original_currency_code` 与 `original_amount`，用来记录商户原始报价。例如 EUR 消费记入 USD 信用卡时，预算按银行最终入账的 USD 金额计算，EUR 原始金额只用于展示和核对。

这两个辅助字段必须同时为空或同时有值。收入和支出报表按账户币种统计，不按辅助原始币种重复统计。

### 币种账本隔离预算

每种启用的币种对应一个币种账本，首版同一币种只允许一个账本。这个限制以家庭共享预算为前提：两位家庭成员的 CNY 预算账户都进入同一个 CNY 账本，共同增加或消耗同一份 CNY `Ready to Assign`。它不会合并不同币种，也不会把一位成员的账户数据覆盖成另一位成员的数据。

分类组、分类名称和备注在所有币种间共享，下面这些数值按币种分别保存：

- 月度分配额
- 分类目标
- 分类活动与可用金额
- `Ready to Assign`
- 超支和补钱
- 信用卡还款分类
- 资金账龄

`computeBudget` 必须接收 `currencyCode`，并且只读取该币种的账户、流水、分配和目标。币种是预算引擎 Interface 的必填条件，不依赖全局状态或前端当前选择。

### 汇总币种只负责列报

设置项 `reporting_currency` 保存全局汇总币种。切换汇总币种只改变换算和展示，原币流水、预算、目标、账户余额以及已经保存的汇率都不重写。

当前净资产按所选估值日最后一个可用汇率换算。历史曲线中的每个月使用该月月末当日或之前最近一个可用工作日的汇率，禁止用今天的汇率重算过去。

每个账户先换算并四舍五入到汇总币种的最小单位，再累加账户换算结果。这样账户明细之和与报表总额严格一致。

## 数据库设计

### `currency_ledgers`

新增币种账本表：

```sql
CREATE TABLE currency_ledgers (
  currency_code TEXT NOT NULL PRIMARY KEY
    CHECK (
      length(currency_code) = 3
      AND currency_code GLOB '[A-Z][A-Z][A-Z]'
    ),
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
);
```

数据库负责校验币种代码的基本形状，Money Module 负责校验代码是否属于当前内置目录。账户币种、原始交易币种和汇总币种都必须穿过 Money Module；界面校验不能代替服务端校验。

### `accounts`

新增 `currency_code`，最终状态为必填，并引用 `currency_ledgers.currency_code`。创建账户接口必须提交币种。Bootstrap、账户列表、账户明细和 AI 账户快照都返回币种。

### `assignments` 与 `goals`

重建两个表并加入 `currency_code`：

- `assignments` 主键改为 `(currency_code, month, category_id)`。
- `goals` 主键改为 `(currency_code, category_id)`。

分类元数据继续共享，所有金额性预算状态按币种隔离。

### `transactions`

权威金额仍是 `amount`，币种从账户继承。新增两个可空字段：

```sql
original_currency_code TEXT,
original_amount INTEGER
```

现有 `pair_id` 继续连接转账的两条腿。跨币种转账允许两条腿拥有不同绝对金额，因此不需要新建一份会与流水金额重复的换汇表。实际汇率由两条腿的币种和金额实时推导。

### `fx_rates`

新增汇率缓存与人工覆盖表：

```sql
CREATE TABLE fx_rates (
  rate_date TEXT NOT NULL,
  base_currency TEXT NOT NULL,
  quote_currency TEXT NOT NULL,
  rate TEXT NOT NULL,
  source TEXT NOT NULL,
  fetched_at TEXT NOT NULL,
  PRIMARY KEY (rate_date, base_currency, quote_currency, source)
);
```

`rate` 保存十进制定点字符串，定义为一个 `base_currency` 等于多少 `quote_currency`。换算使用 `decimal.js`，最后一步才按目标币种精度四舍五入，避免 JavaScript 二进制浮点误差。

人工汇率优先于同日自动汇率。首版自动源使用 [Frankfurter v2](https://frankfurter.dev/)，请求固定带 `providers=ECB`，结果来自欧洲央行参考汇率并缓存到本地。Frankfurter 不需要密钥，支持历史查询；欧洲央行明确这些参考汇率用于信息展示，不建议直接作为交易成交价，因此它们只用于净资产估值。实际换汇始终采用银行真实转出额和到账额。[欧洲央行参考汇率说明](https://www.ecb.europa.eu/stats/policy_and_exchange_rates/euro_reference_exchange_rates/html/index.en.html)

`source` 保存稳定的 Provider 标识，首版自动值使用 `frankfurter_ecb`，人工值使用 `manual`。FX Module 只读写规范化后的汇率记录，不把 Frankfurter 的响应结构泄漏到数据库、报表或前端。以后接入其他来源时新增 Adapter 和 Provider 注册项，不需要迁移账户、交易或预算数据。

### 系统分类

给 `categories` 增加可空且唯一的 `system_key`，创建 `currency_transfer` 系统分类，中文显示为“换汇转出”。名称可以国际化，稳定标识不依赖名称。

预算内账户向另一币种的预算内账户换汇时，转出腿使用该分类，转入腿进入目标币种的 `Ready to Assign`。用户需要像普通支出一样先给“换汇转出”分配资金，这与 YNAB 的独立 plan 做法一致。

## 旧数据库迁移

现有 `currency_symbol` 不能可靠推断币种，`$` 可能代表 USD、SGD、CAD 或其他货币。升级后先进入一次性迁移页，由用户在首版内置目录中确认旧账本币种。符号只用于给出建议，系统不会静默决定。

迁移按下面顺序执行：

1. 在数据变换前生成一份带版本号的本地数据库备份。
2. 新表和新字段先以兼容状态加入，Bootstrap 返回 `currencyMigrationRequired`。
3. 迁移页要求用户选择原账本币种，并把它设为净资产默认币种。
4. 一个数据库事务内创建 CNY、USD、SGD、JPY、EUR 默认币种账本，并创建用户确认的旧账本币种；重复币种只保留一条。随后回填所有账户、分配和目标。
5. 现有金额按旧模型的两位小数换算为目标币种最小单位。CNY、USD、SGD、CAD、EUR 和 GBP 的数值不变；JPY 除以 `100`。
6. 对缩小精度后无法整除的旧金额给出明确明细，用户修正前不提交迁移。
7. 迁移成功后写入完成标记，恢复全部写操作，并保留旧 `currency_symbol` 一个发布周期用于回退显示。

空数据库跳过旧数据迁移，并初始化 CNY、USD、SGD、JPY、EUR 五个默认币种账本。首次设置时要求用户选择净资产默认币种。普通入口新建账户时用净资产默认币种预填；从某个预算账本发起时才用该账本币种预填。保存前始终明确展示账户币种。

数据库升级脚本仍遵守现有只追加迁移的规则。涉及用户选择的数据变换由显式迁移流程完成，启动迁移只增加可兼容的 Schema，不在后台猜测并改写金额。

## Module 和 Interface

### Money Module 集中金额规则

新增 `server/money.mjs`，前端新增对应的 `src/money.ts`，并共用一份受版本控制的币种目录。二者通过同一组行为测试锁定结果，负责：

- 列出首版内置支持的 CNY、USD、SGD、CAD、EUR、GBP、JPY。
- 验证币种是否属于当前内置目录。
- 取得币种最小单位位数。
- 把十进制输入转换为安全整数。
- 格式化带币种代码的金额。
- 使用十进制汇率换算和四舍五入。

业务页面不再维护全局货币符号。`fmtMoney` 的 Interface 改为显式接收 `currencyCode`，金额所在币种从账户或返回数据顶层取得。

### Currency Ledger Module 统一所有写入

把 `server/routes.mjs` 中的交易、转账和对账写入逻辑移到 `server/currency-ledger.mjs`。它是一个深 Module，对 Routes 和 AI 暴露少量 Interface：

```js
postTransaction(input)
postTransfer(input)
reconcileAccount(input)
```

这个 Module 在一个位置维护账户币种、原始金额、转账双腿、同币种守恒、跨币种实际金额、预算分类和事务原子性。HTTP Routes 只负责鉴权、参数解析和返回结果。

AI 不再用任意 `INSERT`、`UPDATE` 或 `DELETE` 绕过这些规则。`run_sql` 保留只读查询，写操作改成调用与网页端相同的类型化工具。用户现有的写前确认开关继续生效。

### FX Module 隐藏汇率复杂度

新增 `server/fx.mjs`，对报表只暴露下面的 Interface：

```js
getRate({ from, to, asOf })
convert({ amountMinor, from, to, asOf })
syncRates({ currencies, dates })
```

FX Module 依赖一个与厂商无关的 Provider Interface：

```js
fetchRates({ base, quotes, fromDate, toDate })
```

Provider 返回规范化的 `rateDate`、`baseCurrency`、`quoteCurrency`、`rate` 和 `source`，不能向上层返回厂商响应对象。首版 Provider 注册表把 `frankfurter_ecb` 映射到 `FrankfurterEcbAdapter`，并把它设为默认值；测试使用 `InMemoryFxAdapter`。首版界面不提供切换自动源的入口，但 FX Module 通过依赖注入接收 Provider。以后增加 MAS、银行或付费数据源时，只需实现同一个 Interface 并加入注册表，Reports Module 和财务数据 Schema 不变。

直连、反向、经 EUR 交叉换算、人工覆盖、本地缓存、工作日回退、来源记录和缺失错误都留在实现内部。人工覆盖属于 FX Module，不属于任何自动 Provider，因此替换自动源不会改变人工值优先规则。所有 Adapter 运行同一套契约测试，至少验证当前内置目录覆盖、实际来源日期、正十进制汇率、禁止未来日期、超时和错误归一化。报表测试只穿过 FX Module 的 Interface，不依赖 HTTP 响应细节。

### Budget 与 Reports Module 按币种工作

`computeBudget` 增加必填 `currencyCode`，预算修改接口也必须带币种。报表拆成两个清楚的 Interface：

```js
buildCashflowOverview({ fromMonth, toMonth })
buildCashflowDetail({ currencyCode, fromMonth, toMonth })
buildNetWorthReport({ reportingCurrency, asOf, months })
```

收支总览返回按账户币种分区的数据，覆盖所有有余额或观察期内有交易的币种，每个币种分别提供收入、支出、净流入和活动状态。单币种详细 Interface 再提供趋势、分类构成、商家和收入来源。拆开 Interface 可以避免一个可选参数改变整个响应形状。不同币种的原始金额保持在独立分区，不能直接相加，也不能共用一根数值轴。净资产报表读取所有账户，通过 FX Module 换算后返回资产、负债、净资产、账户明细和汇率元数据。收支和净资产 Interface 继续隔离原币现金流和汇总列报金额。

### 家庭共享预算使用乐观并发

每个币种账本维护一个 revision。所有会改变该币种预算读模型的写入都在同一事务中推进 revision，包括分配、移动资金、补超支、自动分配、复制上月、目标、预算内账户交易、转账、对账以及预算内账户的创建和关闭。跨币种转账同时推进两个币种账本。

预算写接口接收 `expectedRevision`。版本过期时返回 `409` 和最新预算数据，不执行写入。前端保留用户输入，把输入值与最新值并排展示，由用户决定是否重新提交。分类结构由所有币种共享，首版使用独立的 `categoryRevision` 检查新建、重命名、隐藏和删除；这些操作在确认文案中明确说明会影响所有币种账本。

## 预算与换汇行为

| 转账场景 | 账户流水 | 预算处理 |
| --- | --- | --- |
| 同币种，预算内到预算内 | 两条绝对值相同的腿 | 完全预算中性 |
| 异币种，预算内到预算内 | 两条实际金额不同的腿 | 转出腿记“换汇转出”，转入腿进入目标币种 `Ready to Assign` |
| 预算内到跟踪账户 | 两条腿，异币时分别录入实际金额 | 转出腿使用用户选择的支出分类，跟踪账户不参加预算 |
| 跟踪账户到预算内 | 两条腿，异币时分别录入实际金额 | 预算内转入腿进入该币种 `Ready to Assign` |
| 跟踪账户到跟踪账户 | 两条腿，异币时分别录入实际金额 | 只改变账户余额，不影响预算 |

跨币种转账表单同时显示转出币种和转入币种，要求录入两端实际金额，实时显示隐含汇率。参考汇率只作为对照，不自动替换实际金额。

银行把手续费单独入账时，系统记录一笔普通支出并使用用户选择的手续费分类。手续费包含在银行给出的转出额或到账额时，实际两端金额已经反映费用，不再人为拆分。

预算与报表使用不同视角处理换汇。预算层仍按 YNAB 规则减少转出币种分类余额，并增加转入币种的 `Ready to Assign`。收支报表能看到两条腿属于同一个 `pair_id`，因此把预算账本之间的换汇排除在普通收入和支出之外，另列在“币种调拨”明细中。这样换汇不会被误报成消费或新增收入。

预算账户与投资等跟踪账户之间的转账也排除在普通收支之外，投资视图单独统计净投入和净取回。用户仍然通过投资分类提前安排投入资金，分类活动会如实减少，但 Income v Expense 不把资产内部调拨当成消费。

## 投资账户行为

投资账户保持 `on_budget=0`。用户通过转账记录投入或取回，通过对账把账户调整到券商显示的当前总价值。对账产生的估值调整只改变投资账户余额，排除在 Income v Expense 和日常支出构成之外。

原币投资视图按币种列出：

- 当前投资账户余额
- 账户余额历史
- 本期净投入和净取回
- 最近一次估值日期

“账户余额变化”不命名为“投资收益”，因为没有持仓、现金流时点和成本基础时无法准确计算收益率。所有投资余额按估值日汇率进入统一净资产。

## 汇率与报表行为

### 汇率选择

同币种换算固定返回 `1`。异币种先在本地寻找不晚于估值日的最近可用汇率日期；同一个汇率日期同时存在人工值和自动 Provider 值时，人工值优先。缓存缺少合适日期时才请求自动源，然后用相同规则重新选择。这样较新的自动汇率不会被数月前的人工值长期覆盖，同日人工修正也能稳定生效。

系统绝不使用估值日之后的汇率。自动源失败时保留缓存结果并标记汇率日期；没有任何可用汇率时返回明确的缺失币种对。

### 缺失汇率

缺失任何有非零余额的币种汇率时，统一净资产标记为“不完整”，不显示一个看似精确的总数，也不会把缺失账户按零处理。页面继续显示所有原币余额、已经换算的账户和缺失列表。用户补录人工汇率后重新计算。

### 当前与历史净资产

当前视图默认估值日为配置时区下的今天。历史曲线先取得每个月末的原币账户余额，再使用各月月末可用汇率。账户只从 `starting_balance_date` 当日开始进入历史余额，不能把后来创建的账户期初余额带到更早月份。资产为换算后正余额之和，负债为换算后负余额绝对值之和，净资产为资产减负债。

净资产变化会包含汇率变化和投资估值调整，但两者不会混入原币收入、支出。初版不做净资产变化归因，避免把报表换算差额错误解释成消费或投资收益。

### 缓存和离线

打开统一净资产页时只拉取本地缺少的日期和币种，已经缓存的汇率不重复请求。HTTP 请求设置短超时，失败后立即使用缓存。原币预算、账户、交易和投资视图从不依赖网络。

设置页提供汇率状态、手动刷新和人工覆盖入口，显示最后更新时间和来源。外部请求只包含币种代码和日期，不发送账户名称、余额或流水。

## 前端与接口改动

### Bootstrap 与类型

`Settings` 增加 `reportingCurrency`、`supportedCurrencies` 和迁移状态。`supportedCurrencies` 来自服务端 Money Module，前端不再复制一份币种目录。`Account` 增加 `currencyCode`。`BudgetData`、原币报表和净资产报表在顶层明确返回币种，金额字段在顶层币种范围内保持整数，避免给每个数字套重复对象。

`currencySymbol` 进入兼容期，所有新代码使用币种代码和 `Intl.NumberFormat` 生成符号、分组和小数位。

### 页面交互

- Sidebar 显示全部账户及分币种小计，不放跨页面的活动币种选择器。
- Budget 页在标题区显示“预算账本”选择器，并只读取这一币种的预算数据。币种写进 URL；当前设备最近值只供无参数入口回退，不改变其他家庭成员的页面。
- Accounts 页先按预算内和跟踪账户分组，再按币种显示原币小计；跨币种家庭总额通过“查看家庭净资产”进入报表，不在账户页隐式换算。
- Transactions 页金额使用所属账户币种。跨账户筛选同时展示币种，外币消费标明“账户入账／商户计价”，异币转账标明“转出／入账”。
- Reports 页按用户问题分为“收支（按币种）”“投资”和“家庭净资产”。收支总览默认用列表或卡片展示各币种独立摘要，完整图表留在单币种详情；家庭净资产明确显示“折算为 CNY”一类有角色的控件。预算账本、收支筛选、净资产折算币种和估值日都写进 URL。
- Settings 页用“净资产默认币种”替代“货币符号”，增加汇率覆盖状态、刷新和人工覆盖管理。自动缓存明细收进高级区域。报表页可以临时切换折算币种，不改家庭默认值。
- Settings 页显示默认启用的 CNY、USD、SGD、JPY、EUR，并允许从内置支持目录继续启用 CAD 或 GBP。
- 新建账户必须从已经启用的币种中选择，通常默认取家庭的净资产默认币种；从某个预算账本发起时默认取该账本币种。保存前始终明确展示。

所有新增文案同时补齐中文和英文。界面不使用单独的 `$` 判断币种，避免 USD、CAD 等符号冲突。

### HTTP Interface

现有路径尽量保留，通过显式参数增加币种：

```text
GET  /api/budget/:month?currency=USD
GET  /api/reports/cashflow?months=12
GET  /api/reports/cashflow/USD?months=12
GET  /api/reports/net-worth?reportingCurrency=CNY&months=12&asOf=2026-08-30
POST /api/accounts                 { ..., currencyCode }
POST /api/transactions             { ..., originalCurrencyCode?, originalAmountMinor? }
POST /api/transfers                { fromId, toId, fromAmountMinor, toAmountMinor? }
POST /api/fx/sync
PUT  /api/fx/rates/:date/:from/:to
```

同币种转账省略 `toAmountMinor` 时默认与转出绝对值相同。异币种转账必须提交两端金额。服务端根据账户币种判断，拒绝模糊输入。

预算写接口另带 `expectedRevision`；发生并发冲突时返回 `409`、最新 revision 和最新预算数据。分类结构写接口使用 `expectedCategoryRevision`，避免两台设备静默覆盖共享分类。

## AI 与 IM 记账

AI 的 Schema 文档、账户快照和视觉记账说明全部改为币种感知：

- 账户快照显示币种和按该币种格式化的余额。
- 不再宣称所有金额都是“分”或固定除以 `100`。
- 图片中识别出的原始币种无法确定账户入账金额时，AI 先询问或只提出待确认写入，不能自行套参考汇率。
- 普通交易调用 `post_transaction` 工具，跨币种转账调用 `post_transfer` 工具。
- 创建账户、分配预算、设置目标、对账和修改分类备注也改用类型化工具。现有 AI 能完成的写入场景先达到功能对等，再收紧 SQL 权限。
- `run_sql` 最终只允许读取财务表，`fx_rates`、迁移状态和内部设置禁止 AI 写入。
- 写操作继续沿用网页与 IM 共用的确认策略。

这样 Routes、网页聊天和 IM 都穿过 Currency Ledger Module 的同一 Interface，币种规则只维护一份。

## 验收场景

以下场景全部通过才算功能完成：

- 旧两位小数账本选择 CNY 后，余额、预算和历史报表数值与升级前一致。
- 旧账本选择 JPY 时，迁移正确缩放金额；存在非整日元金额时迁移明确阻止并列出异常。
- 新家庭默认存在 CNY、USD、SGD、JPY、EUR 五个币种账本，CAD 和 GBP 不默认创建。
- 用户可以从内置目录继续启用 CAD 或 GBP，并在相应币种下创建账户和预算。
- 首版公共写入 Interface 拒绝目录外币种。测试目录临时加入 AUD 后，无需修改数据库 Schema 就能创建 AUD 币种账本，证明目录可以扩充。
- 两位家庭成员各自名下的 CNY 预算账户共同进入同一个 CNY 账本，两人的收入相加进入同一份 CNY `Ready to Assign`，流水仍按账户分别保存。
- SGD 工资只增加 SGD 的 `Ready to Assign`，不会改变 CNY 预算。
- 同一个“餐饮”分类可以同时拥有 SGD 和 CNY 的不同目标、分配额与可用金额。
- `100 SGD` 换成 `550 CNY` 后，两边账户分别变化 `100 SGD` 和 `550 CNY`，目标币种新增 `550 CNY` 待分配资金。
- 同一笔换汇出现在“币种调拨”中，不增加普通收入或支出。
- EUR 消费记入 USD 信用卡时，预算只使用 USD 入账金额，同时能够查看 EUR 原始金额。
- USD 投资账户通过对账增加价值后，USD 投资余额和统一净资产更新，Income v Expense 不新增收入。
- 汇总币种为 CNY 时，CNY 现金、USD 投资、SGD 银行存款和 JPY 现金按估值日汇率得到可复算的资产、负债和净资产。
- 历史净资产使用各月月末汇率。修改今天的人工汇率不会改变过去月份，除非用户也修改对应历史日期。
- 后来创建的账户不会出现在 `starting_balance_date` 之前的历史净资产中。
- 某个非零余额币种缺失汇率时，页面展示缺失项并停止输出统一总数。
- 断网时原币记账和预算完整可用；已有汇率的统一净资产仍可查看并标明汇率日期。
- AI 创建普通交易和跨币种转账时穿过类型化工具，无法绕过币种和双腿约束。
- AI 仍能创建账户、分配预算、设置目标、对账和维护分类备注，写前确认行为与升级前一致。

## 验证和发布

详细测试设计保存在 [test-plan.md](./test-plan.md)，里面给出了现有测试基线、Money 与各业务 Module 的行为矩阵、固定家庭夹具、旧数据库副本迁移演练和浏览器手工验收。开始编码前先用 CI 同款 Node 20 跑出绿色基线；每个检查点按测试计划留下 RED、GREEN 和全量回归证据。

每个 RED 阶段运行目标测试并保存预期失败原因。每个 GREEN 和 REFACTOR 阶段至少运行相关测试，检查点提交前运行：

```bash
npm run typecheck
npm test
npm run build
```

最终还要用一份生产数据库副本演练迁移，逐项核对迁移前后的账户余额、每月 `Ready to Assign`、分类可用金额、净资产和交易数量。演练副本不替换用户数据库。

实现使用 `codex/multi-currency` 工作树分支，通过 PR 合入 `dev`。CI 的 typecheck 和测试必须通过。涉及真实旧库的升级先自动备份；如果迁移后发现问题，回退方式是恢复升级前备份，不能把新 Schema 直接降级。

## 完成定义

功能完成需要同时满足：

- 所有金额计算都能指出币种，没有依赖全局符号或固定两位小数的代码路径。
- 预算、收入和支出在币种间完全隔离。
- 跨币种转账使用实际两端金额，原子写入并可对账。
- 投资账户保持预算外，进入净资产但不污染收支。
- 当前和历史统一净资产都有明确汇率日期与来源，缺失汇率不会生成错误总数。
- 默认自动汇率使用 Frankfurter ECB Adapter，替换 Provider 不需要修改报表或迁移财务数据。
- 网页、AI 和 IM 使用同一套写入规则。
- 旧账本迁移经过备份、用户确认、数值核对和回滚演练。
- 中英文界面、README、演示数据、类型和测试同步更新。
- `npm run typecheck`、`npm test`、`npm run build` 和目标迁移验收全部通过。
